El problema que resuelve

La suplantación de identidad mediante inteligencia artificial creció más rápido que la capacidad de la gente para reconocerla. Existe información dispersa sobre el tema, pero poca en un formato que sirva a la vez para aprender a identificarla, saber qué hacer si ocurre y dejar constancia del caso.

Alerta Deepfake reúne esas tres cosas en un solo sitio: material educativo con respaldo en la normativa colombiana, un simulador para entrenar el criterio propio, y un sistema de reportes con almacenamiento real de evidencia.

Alcance honesto: este sitio no analiza automáticamente si un archivo es un deepfake. No hay un modelo de detección detrás. Lo que hace es educar, orientar y registrar casos. Decir lo contrario sería vender algo que el proyecto no tiene.
Decisiones de arquitectura

Con qué está hecho, y por qué

HTML, CSS y JavaScript sin frameworks

Un sitio de cinco páginas con un formulario y un panel no justifica React ni Vue. Sin framework el proyecto carga más rápido, no arrastra dependencias que envejecen, y —lo más importante para un trabajo académico— cada línea es explicable sin decir "eso lo hace la librería".

Node.js con Express

Mismo lenguaje en el navegador y en el servidor, lo que reduce el costo de cambiar de contexto mientras se desarrolla. Express aporta el enrutamiento y los middlewares sin imponer una estructura rígida.

PostgreSQL

Los datos del proyecto son claramente relacionales: un reporte pertenece a una categoría y puede tener varias evidencias. Esas relaciones se expresan con claves foráneas y se protegen con restricciones a nivel de motor, no a punta de confiar en el código.

Docker Compose

Cuatro servicios (base de datos, API, servidor web y pgAdmin) que se levantan con un solo comando y funcionan igual en cualquier máquina. Elimina el clásico "en mi computador sí funciona" a la hora de sustentar.

Nginx como puerta de entrada

Sirve el frontend estático y redirige /api/ al backend. Así el navegador habla con un solo origen: no hay problemas de CORS y el backend puede quedar oculto de la red externa.

Sin ORM

Se usa el driver pg con consultas parametrizadas escritas a mano. Para un esquema de tres tablas, un ORM habría añadido una capa de abstracción difícil de justificar frente al beneficio de ver y entender el SQL exacto que se ejecuta.

Decisiones de seguridad

Cómo se protege

Un sitio que recibe denuncias y archivos de desconocidos es, por definición, un blanco. Las defensas se agrupan en cuatro frentes:

Entrada de datos

Todo lo que escribe un usuario se valida en el servidor y se inserta como texto, nunca como código.

Archivos subidos

Se verifica el contenido real del archivo, no su extensión, y se guarda con un nombre aleatorio.

Acceso al panel

Contraseña comparada en tiempo constante, sesión firmada y límite de intentos.

Secretos y errores

Credenciales solo por variables de entorno; los errores internos nunca llegan al cliente.

Bitácora de incidentes

Retos durante el desarrollo

Ninguno estaba planeado: todos aparecieron durante el desarrollo real. Despliega cada uno para ver la causa raíz y cómo se resolvió.

1 Contraseñas por defecto en el repositorio Valores débiles que se habrían publicado en GitHub

Problema: el docker-compose.yml traía contraseñas escritas directamente en el archivo y valores por defecto débiles.

Solución: se movieron a variables de entorno obligatorias. Si falta una, Docker se niega a arrancar con un mensaje claro en vez de usar silenciosamente una clave insegura.

Fallar ruidosamente es preferible a funcionar de forma insegura.

2 La contraseña nueva no servía para entrar a la base de datos PostgreSQL seguía usando la clave original

Problema: tras cambiar la contraseña en el archivo de entorno, el backend seguía recibiendo authentication failed.

Causa raíz: PostgreSQL solo aplica la contraseña la primera vez que se crea su volumen de datos. Como el volumen ya existía, conservaba la clave original.

Solución: actualizarla dentro del motor con ALTER USER, en lugar de borrar el volumen —que habría destruido todos los reportes ya guardados—.

Antes de borrar algo para arreglarlo, verificar qué datos se lleva por delante.

3 La evidencia se "guardaba" pero no llegaba nunca Un fallo silencioso, sin ningún mensaje de error

Problema: al adjuntar un archivo, el reporte se registraba con éxito pero la tabla de evidencias quedaba vacía y no aparecía ningún error.

Causa raíz: el navegador ejecutaba una versión anterior del JavaScript desde su caché. Esa versión enviaba el formulario como JSON, formato en el que un archivo simplemente desaparece. Los demás campos sí llegaban, y por eso todo parecía correcto.

Solución: en vez de seguir modificando código a ciegas, se añadieron registros temporales en el servidor para ver exactamente qué llegaba. Confirmaron que era el caché y no la lógica.

Ante un fallo silencioso, primero observar los datos reales; después tocar el código.

4 Una dependencia con vulnerabilidad conocida Sin parche disponible para una versión compatible

Problema: la librería elegida para verificar el contenido real de los archivos tenía una vulnerabilidad de denegación de servicio, sin parche para una versión compatible con el proyecto.

Solución: se reemplazó por una verificación propia de unas 50 líneas, acotada a los nueve formatos que el sitio realmente acepta. Menos superficie de ataque, sin dependencias externas y totalmente auditable.

Una librería genérica traía riesgo por formatos que este proyecto nunca iba a recibir.

5 Los archivos subidos daban error 404 Nginx trabajaba con la configuración anterior

Problema: el archivo se guardaba correctamente y quedaba registrado en la base de datos, pero al abrir su enlace aparecía un 404 de Nginx.

Causa raíz: se había añadido la nueva ruta a la configuración, pero ese contenedor nunca se reinició.

Cambiar un archivo de configuración no basta: hay que confirmar que el servicio lo releyó.

6 Credenciales filtradas al repositorio público Las cuatro contraseñas reales, subidas por accidente

Problema: un archivo de texto con el contenido completo del archivo de entorno se subió por accidente a un repositorio público.

Solución: primero rotar las cuatro credenciales, porque borrar el archivo no deshace el hecho de que estuvieron expuestas; después reescribir el historial de Git con git filter-repo para eliminarlas de todos los commits anteriores, y resincronizar ambas máquinas.

Ante una filtración el orden importa: rotar primero, limpiar después.

Cómo se trabajó

El desarrollo se hizo entre dos equipos con roles distintos, sincronizados mediante Git y GitHub:

PC de escritorio — edición

Escritura de código y control de versiones. Se conecta por SSH al portátil cuando hace falta ejecutar algo.

Portátil Linux — ejecución

Aquí viven Docker, PostgreSQL y el servidor. Es el entorno donde el proyecto realmente corre y se prueba.

La regla para evitar trabajar sobre dos copias divergentes: los cambios se confirman y se suben desde el equipo de edición, y se traen con git pull antes de ejecutar en el portátil. GitHub actúa como única fuente de verdad.
